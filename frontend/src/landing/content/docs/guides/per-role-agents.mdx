---
title: Per-role agents
description: Configure separate harnesses and models for worker and orchestrator sessions.
---

AO has two session roles:

- A **worker** implements a focused task in an isolated workspace and may own pull requests.
- An **orchestrator** supervises a project, monitors sessions, and delegates implementation to workers.

Role and interface are separate choices. Either role can start in structured Chat or Terminal UI when its harness supports that interface.

## Configure roles

Open the project settings in the desktop app and choose the worker and orchestrator agents. The CLI can set the initial agents while registering a project:

```bash
ao project add --path /absolute/path/to/repo \
  --worker-agent codex \
  --orchestrator-agent claude-code
```

For a full configuration replacement, the stored JSON shape is:

```json
{
  "worker": {
    "agent": "codex",
    "agentConfig": {
      "model": "gpt-5.4",
      "permissions": "bypass-permissions"
    }
  },
  "orchestrator": {
    "agent": "claude-code",
    "agentConfig": {
      "model": "claude-opus-4"
    }
  }
}
```

## Role profiles

A profile is a named bundle a role or a single spawn can name instead of repeating the harness, agent config, rules and environment. Define profiles under `profiles`, point a role at one with `worker.profile` or `orchestrator.profile`, and pick one per spawn with `ao spawn --profile <name>`; `--agent` and `--model` still override what the profile sets. A profile's set fields win over the role override's inline ones; its `rulesFile` is appended after the project rules; its `env` keys win over the project's.

```json
{
  "worker": { "profile": "flash-coder" },
  "orchestrator": { "agent": "claude-code" },
  "profiles": {
    "flash-coder": {
      "agent": "agy",
      "agentConfig": { "model": "gemini-3.8-flash-high", "permissions": "bypass-permissions" },
      "rulesFile": "rules/flash-coder.md"
    },
    "pro-expert": {
      "agent": "agy",
      "agentConfig": { "model": "gemini-3.1-pro-high", "permissions": "bypass-permissions" },
      "rulesFile": "rules/pro-expert.md"
    }
  }
}
```

The session remembers its profile, so a restore folds the same bundle back in. Standing rules are layered general to specific: the daemon's operating contract when `<data dir>/rules/contract.md` exists, the project's rules, then the profile's rules file. A reviewer entry can name a profile too (`"reviewers": [{ "harness": "agy", "profile": "pro-expert" }]`); the profile's harness and agent config are read at review time, so editing the profile reaches the next review.

## Quota admission

A profile on Antigravity (`agy`) can gate spawns on the plan's remaining capacity, which every Gemini model on the plan shares:

```json
{
  "profiles": {
    "flash-coder": {
      "agent": "agy",
      "agentConfig": { "model": "gemini-3.8-flash-high" },
      "quota": { "warnBelowPercent": 20, "refuseBelowPercent": 0 },
      "fallback": { "profile": "paid-expert" }
    },
    "paid-expert": { "agent": "claude-code" }
  }
}
```

At spawn the daemon reads the capacity snapshot (cached for two minutes, the worse of the 5-hour and weekly windows). At or below `warnBelowPercent` the spawn proceeds and the daemon logs a warning; at or below `refuseBelowPercent` the task goes to the `fallback` profile instead (checked once against its own quota, its fallback not followed), or the spawn fails with `SPAWN_QUOTA_EXHAUSTED` when there is none. Explicit `--agent` on another harness is never gated, and an unreadable snapshot leaves capacity advisory rather than blocking work.

## Workflow templates

A template names which profile fills each role slot, plus the orchestrator's delegation plan, so "Flash implements, Pro reviews" is one switch rather than three edits. Define templates under `templates` and bind one with `ao project apply-template <project-id> <name>` (or the Templates tab in project settings): the worker and orchestrator slots take the template's profiles, the reviewer list is replaced by its reviewer profiles, and `template` records which one is active. A template never changes a profile.

```json
{
  "templates": {
    "flash-first": {
      "orchestrator": "orchestrator",
      "worker": "flash-coder",
      "reviewers": ["pro-expert"],
      "orchestratorRulesFile": "rules/plan-flash-first.md"
    }
  }
}
```

While a template is active, its `orchestratorRulesFile` is appended last to the orchestrator's standing rules: the plan that tells the orchestrator which profile takes which kind of task, in your words, so the per-task choice stays the orchestrator's.

Pass the object itself with `ao project set-config <project-id> --config-json '<json-object>'`; the flag does not read a file. This replaces the project config, so preserve any existing setup, rules, reviewers, or intake fields.

## Start an orchestrator or worker

The desktop provides dedicated new-session and orchestrator flows. From the CLI:

```bash
ao spawn --project my-project --kind orchestrator \
  --name supervisor --mode chat

ao spawn --project my-project --kind worker \
  --name issue-42 --issue 42 --mode tui
```

`--name` is required and limited to 100 characters. `--harness` overrides the role's configured agent for one spawn.

## Choose Chat or Terminal UI

- Use **Chat** for structured messages, provider activity, approvals, plans, changed files, usage, compaction, and rollback. Current native drivers cover Codex, Claude Code, OpenCode, and Droid.
- Use **Terminal UI** when you want the agent's native interface or a harness without native Chat support.

Compatible Claude Code and Codex sessions expose **Open Chat** or **Open Terminal UI**. Idle sessions switch directly. When work is active, AO asks whether to finish and drain it or stop and interrupt it before switching controllers.

## Project rules

Use `agentRules` and `agentRulesFile` for worker instructions. Use `orchestratorRules` for supervision-specific guidance. These are stored in the typed project config and injected into the appropriate session role.

	AO uses the provider CLI already installed and authenticated on your machine. Run `ao doctor` if a configured harness fails preflight.
</Callout>
